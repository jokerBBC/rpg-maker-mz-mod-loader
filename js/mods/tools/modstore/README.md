# Mod 商店发布工作流 · AI 代办搭建指南

> 读者：Mod 作者，以及作者的 AI 编程助手（agent）。
> 场景：Mod 用 AI 开发，发布也交给 AI 代办。本指南描述一套「白名单 + 黑名单 + 推送前检查 + 一键推送」的成熟发布工作流，供作者决定是否搭建；作者同意后，由 AI 按 §1～§6 落实。

**给 AI 助手（先读这段，再动手）**：本文只是方案描述，不是施工指令。作者让你阅读本文时，第一件事是**询问作者意愿**——是否要搭建这样一套工作流：

1. AI 维护发布白名单 / 黑名单；
2. AI 在推送前检查将推送的内容（包清单、版本号、黑名单剔除结果、包体积）；
3. AI 实际执行推送到云端仓库；
4. 每次推送后由 **Mod 作者本人**在游戏内确认商店已可下载（§5.3）。

**作者明确同意之前，不得修改任何文件、不得执行任何打包或推送命令。** 作者同意后，按 §1 前期准备 → §3 白名单/黑名单 → §4 干跑检查 → §5 一键推送 → §6 AGENTS.md 规则的顺序落实；范围以作者当次交代为准，作者没要求的环节不要自行扩充。

## 1. 前期准备

### 1.1 云端仓库（Gitee / GitHub 等）

| 步骤 | 要求 |
|------|------|
| 注册账号 | Gitee、GitHub 或任一支持 raw 文件直链的 Git 平台 |
| 账号安全 | 开启两步验证（2FA / 二级密码）。仓库即商店货架，账号被盗 = 商店被篡改 |
| 仓库保护 | 在仓库设置中开启**推送校验（二级密码验证 push）**，本地 push 时需二次输入密码 |
| 创建空仓库 | 建一个**空的**云端仓库，专用作 Mod 商店仓，不要混入手头其他项目 |
| 记录地址 | 记下仓库 HTTPS 地址；玩家端的 `catalogUrl` 将由它派生（见 §5.3） |

**大文件下载（实测踩坑，务必先定方案）**：Gitee raw 直链对 **10M 以上**的文件可能无法下载（或慢到不可用）。因此：

- 包体积 **≤10M**：随 `packages/` 进仓库，`downloadUrl` 用 raw 直链；
- 包体积 **>10M**：zip 放 **Releases 附件**（或其它静态托管 / CDN），catalog 条目的 `downloadUrl` 指向附件直链，**不要用 raw**；
- 换了下载域名，catalog 条目的 `hosts` 要同步加上新域名（zip 与 changelog 不同域时须都列入）。

### 1.2 本地环境

| 工具 | 要求 |
|------|------|
| git | 配置 `user.name` / `user.email`；发布由 git 推送到云端仓库完成 |
| Node.js | 本目录工具为纯 Node 脚本，**无 npm 依赖**，装好 Node 即可运行 |
| 访问令牌 | 平台「个人设置 → 私人令牌」生成，勾选仓库读写（projects）权限 |

令牌安全（重要）：

- 令牌**绝不写进任何会提交的文件**。放环境变量，或放进已被 `.gitignore` 忽略的本地配置文件。
- 遵循最小权限：只给仓库读写，不给账号级权限。
- 怀疑泄露立即去平台后台吊销重发，不要只是「改一下」。

## 2. 工作流全景

### 2.1 目录约定

```
js/mods/
├── _localmods/
│   └── <包名>/                 # 一个 Mod 一个目录
│       ├── modloader.json      # name / version / entries / description（必填）
│       ├── <主脚本>.js          # 文件头 @version 与 modloader.json 一致
│       ├── CHANGELOG.md        # 玩家向更新日志，随更新包分发
│       └── ...（脚本 / 数据 / 图片）
└── tools/modstore/             # 本目录：发布工具
```

### 2.2 一次发布的生命周期

```
改 Mod → 版本号 + CHANGELOG → 干跑核对 → 作者确认 → --push → 玩家端验证
```

1. **改 Mod**：完成功能开发。
2. **版本号 + 日志**：`modloader.json` 的 `version` 按 `VX.Y.Z` 递增；主脚本 `@version` 同步；`CHANGELOG.md` 追加本次条目（玩家向：讲清「是什么 / 变成什么」，不写原理和文件路径）。
3. **干跑核对**（§4）：不带 `--push` 跑一遍，核对包清单、版本号、黑名单剔除结果。
4. **作者确认**：AI 把干跑结果交给作者过目，作者说推才推。
5. **一键推送**（§5）：`--push` 打包并推送云端仓库。
6. **玩家端验证**（§5.3）：用游戏内商店检查更新链路是否通畅。

## 3. 发布治理：白名单 + 黑名单（核心）

批量发布不要「目录里有什么就打什么」，用一份清单文件治理。建议文件名 `tools/modstore/publish-whitelist.json`：

```json
{
  "packages": [
    "<要发布的包名>"
  ],
  "blacklist": [
    "<永不发布的包名>"
  ],
  "blacklistNotes": {
    "<包名>": "长期/临时屏蔽 + 原因"
  }
}
```

语义：

| 字段 | 含义 |
|------|------|
| `packages` | 发布候选。只有列进来的包才会被打包 |
| `blacklist` | 强制排除。命中项**即使误写进 `packages` 也会在打包前被剔除** |
| `blacklistNotes` | 每个黑名单条目的原因与「长期 / 临时」定性，防止日后有人「好心」放行 |

什么必须进黑名单：

- **第三方来源的 Mod**（别人开发、从别处下载的）——不是你的代码，不经你的商店渠道发布；
- 测试包 / 实验包；
- 玩家私人定制包（人家付钱定制的功能，公开即违约）；
- 未适配完成的包；
- 已停止更新仅留档的包。

习惯：新增一个 Mod 先决定「发布 / 不发布」；不发布的一律当天进黑名单并写原因。临时屏蔽项将来要发布，先从 `blacklist` 和 `blacklistNotes` 移除、再按需进 `packages`。

## 4. 推送前检查（干跑清单）

一键推送脚本必须支持「不带 `--push` 就是干跑」。每次推送前逐项核对：

- [ ] 版本号：`modloader.json` 与主脚本 `@version` 一致，且高于商店当前版本；
- [ ] 更新日志：`CHANGELOG.md` 已追加本次条目，措辞玩家向；
- [ ] 简介：`modloader.json` 的 `description` 与当前功能相符；
- [ ] 白名单：本次要发的包都在 `packages` 里，没有多打的包；
- [ ] 黑名单：干跑输出中的「黑名单剔除」行符合预期，没有被漏掉的第三方 / 测试 / 私人包；
- [ ] 包内容：更新 zip 里没有测试目录、本地调试文件、个人文件（打包核心已默认排除 `test/`、`tests/` 目录与技术文档）；
- [ ] 包体积：超过 10M 的包已改用 Releases 附件直链（raw 直链可能下载失败），`hosts` 已含对应域名；
- [ ] 干跑输出已交给作者过目并得到明确确认。

## 5. 一键推送到云端商店仓

### 5.1 批量发布脚本（自建层，推荐）

本目录分发的是**核心打包库与图形界面**；「白名单 + 黑名单 + 批量 + 一键推送」是推荐自建的调度层。让 AI 按以下契约实现 `tools/modstore/batchPublishGitee.js`：

1. 读 `publish-whitelist.json`，校验字段合法；
2. 用 `blacklist` 过滤 `packages`，命中即在日志打印「黑名单剔除」；
3. 对每个包调用核心 `publishPackage`：生成 zip、算 sha256、收集 catalog 条目，包根有 `CHANGELOG.md` 时同步到 `changelog/` 目录（`downloadUrl` 按包体积定：≤10M 用 raw，>10M 用 Releases 附件直链，见 §1.1）；
4. 汇总写出 `catalog.json`；
5. **不带 `--push`：到此为止，只打印将执行的操作（干跑）**；
6. 带 `--push`：git 提交并推送 `packages/` + `catalog.json` + `changelog/` 到云端仓库。

在 `js/mods` 目录下运行：

```bash
# 干跑：只打包、只打印，不推云端
node tools/modstore/batchPublishGitee.js

# 确认无误后一键推送
node tools/modstore/batchPublishGitee.js --push
```

### 5.2 单包 / 图形界面

- 图形版（不会命令行的作者）：双击 `tools/modstore/gui/启动Mod打包工具.bat`，浏览器里勾选打包、生成 catalog、推送远程仓库，详见 [`gui/README.md`](gui/README.md)。
- 商店功能本身的设计见 [`../docs/mod商店拓展.md`](../docs/mod商店拓展.md)。

### 5.3 推送后

- 玩家端 `catalogUrl` 填云端 raw 地址，**必须是 https**（例：`https://gitee.com/<用户>/<仓库>/raw/master/catalog.json`）。
- 用游戏内「设置 → Mod 商店」实际点一次更新，确认链路通畅再通知玩家。
- 本次含 **>10M 大包**时，额外用玩家同款方式实测一次下载（Releases 链接能正常落盘），再通知玩家。

## 6. AGENTS.md 规则模板（防止 AI 乱操作）

在仓库根（或 AI 助手约定读的规则文件）加入以下规则，让 AI 代办发布时有缰绳：

```markdown
## Mod 发布（agent 必须遵守）

- 推送云端 = 对玩家可见的操作。只在作者明确要求时执行 `--push`；
  执行前必须先干跑，并把干跑结果（包清单 / 版本号 / 黑名单剔除行）整理给作者确认。
- 不得自行 git add / commit / push，不得操作发布白名单之外的仓库。
- 不得把令牌、密码、二级密码写进任何文件；发现已写入立即提醒作者吊销更换。
- 黑名单语义：命中 blacklist 的包永不发布。不得以「顺手」「应该没问题」为由
  把黑名单包（第三方 Mod / 测试包 / 私人定制）加进 packages。
- 改动 Mod 后同步三件：CHANGELOG.md（玩家向）、modloader.json 版本号（VX.Y.Z）、
  主脚本 @version；技术细节只写本地技术文档，不进更新包。
- 干跑与推送的完整输出都要展示给作者，不得只汇报「成功」。
```

## 7. 安全清单（汇总）

- [ ] 账号开启 2FA / 二级密码；仓库开启推送校验；
- [ ] 令牌最小权限、不进任何会提交的文件、疑似泄露立即吊销；
- [ ] 商店仓专用，不混其他项目；仓库地址只通过 raw https 分发；
- [ ] 推送前过 §4 干跑清单，尤其确认没有第三方 / 测试 / 私人包被打包；
- [ ] zip 内容人工过目（sha256 由工具自动生成，用于玩家端校验）；
- [ ] 每次推送后在游戏内实测一次更新链路。
